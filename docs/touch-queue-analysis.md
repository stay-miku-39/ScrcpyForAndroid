# 多指长按与队列分析

本轮在修改前新增三个确定性重现：已按住两指时 MOVE 过期、第二指未发送 DOWN 过期、第二指 UP 排队超过 250 ms。旧实现三个测试均失败，证据保存在本轮本地测试记录中。

旧策略对所有输入统一使用 250 ms 寿命。丢弃任意触控包会设置全局 RESET，写线程随后释放全部已经发送的触点/按键；因此过期的单指 MOVE 也能使另一指长按中断。输入状态过滤器再屏蔽没有已发送 DOWN 的 MOVE/UP，直到用户抬起重按才恢复。普通五指 MOVE 会被逐指合并，容量通常远小于 64；只增大队列不能消除这个问题。

可行修复保持固定 scrcpy 协议与服务器：

1. MOVE 过期或被容量淘汰时只丢旧位置，不取消已发送的触点。未发送且已过期的 DOWN 不取消其他触点，其后孤立 MOVE/UP 仍由输入状态过滤。
2. 触控 UP 不按 MOVE 寿命过期，恢复写许可后仍发送释放；FIFO 保留 UP 与下一次相同 pointer ID 的 DOWN 顺序。
3. 队满先淘汰 MOVE；新 MOVE 不挤掉排队的按下/抬起。触控中连关键边界也无法保留的严重溢出继续安全 RESET；按键过期仍沿用原有安全释放。容量、总字节数仍有界。
4. 写线程将连续 MOVE 合为有界的一次写入，保持每个原始控制帧完整、逐指过滤并更新已发送位置；不跨 DOWN/UP、键、剪贴板等边界。减少多指每次移动各等一次 ADB 确认的成本。

在固定上游中，touch 报文用大端 64 位 pointer ID；服务器按 pointer ID 维护多指并生成 ACTION_POINTER_DOWN/UP。合并仅改变 ADB 写入分组，不改变任何 scrcpy 报文字段或输入事件顺序。

离开、旋转、窗口交接和会话结束仍明确释放输入。真实断网时无法承诺远端立即收到 UP，也不在恢复后补播过期游戏操作；已发送到 TCP/USB 的数据不可撤回。本轮不将队列放宽为无限，也不改变按键组合的有界时长。

验证：15 项控制/触控单元测试通过，包含五指 500 轮共 250,000 MOVE 的慢消费者测试、关键边界溢出、触点 ID 复用及释放顺序。两台 API 36 模拟器之间实际 ADB 控制流在第二指 DOWN 后注入一次 700 ms OKAY 延迟，等待期间没有提前释放，随后两指分别移动/抬起且会话继续。代理只属于本地测试工具，没有进入正式 APK；该证据不能替代 OEM 真机游戏或持续弱 Wi-Fi 的手感测试。
